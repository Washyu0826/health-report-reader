## R9 — latency (v4 prompt) and knowledge-base content (2026-09-28)

v4 prompt: rule-derived conditions/risks are no longer re-generated by the LLM; it writes only a summary,
advice and text-stated conditions (fewer output tokens), plus keep_alive, one batched query-embedding call
and streamed output for the UI. Same judge as R3–R8 (qwen3:8b); "relevant" = advice judged directly
relevant to this patient's findings. Settings: dense, LangGraph path, unsupported advice dropped,
public reference ranges (`data/reference_ranges.json`) for both sets.

**Prompt × KB (synthetic quick set, 10 reports) — paired runs on the same day**

| Prompt | KB | Advice relevant | Latency p50 |
|---|---|---|---|
| v3 | 57 targeted passages | 43.8% | 17.3 s |
| v3 | 152 targeted passages | 35.6% | 17.0 s |
| v4 | 57 targeted passages | 43.4% | **9.1 s** |
| v4 | 152 targeted passages | 35.1% | 11.4 s |
| v4 | 152 + per-finding tag routing (`applies_to`) | 34.8% | 10.7 s |
| v4 | generic corpus (~3,600 passages, private) | 30.0% | 11.8 s |

The v3 × 57 cell re-runs the R6q-drop configuration: 47.2% then, 43.8% now, so differences of about
3 points are noise at this sample size.

**KB on the internal set (12 real de-identified reports, v4)**

| KB | Advice relevant | KB citations supported |
|---|---|---|
| generic corpus | 25.3% | 64% (78/122) |
| **57 targeted passages** | **34.9%** | 80% (84/105) |
| 152 targeted passages | 15.6% | 89% (101/114) |
| 152 + tag routing | 19.8% | 85% (88/104) |

Findings:
* The v4 prompt halves LLM latency (p50 17 s → 9 s) at no measurable cost in advice quality (43.8% vs 43.4%).
* KB content matters more than retrieval algorithms, but **more passages is not better**: growing the targeted
  set from 57 to 152 passages lowered advice relevance on both sets, and per-finding tag routing did not
  recover it. The default KB is back to the 57 passages; the 152 are kept as `data/kb_sample_extended.json`.
* The targeted 57 passages beat the generic corpus on real reports too (34.9% vs 25.3%).

**Latency profile** (`eval/profile_latency.py`, quick set, pipeline, RTX 4060 Laptop 8 GB):
total p50 9.7 s / p95 32.0 s; first useful result (findings + rule conditions) p50 0.11 s; LLM p50 8.0 s
(~307 output tokens at 45.6 tok/s decode; prefill ~2,200 tok/s). p95 is the scanned PDFs: OCR takes ~31 s and
swapping the OCR and chat models costs one ~4.5 s reload.

Known limitation (internal set, public ranges): LH / FSH are judged against adult sex-specific ranges with no
cycle-phase or menopause context, so when a report prints no range for them, values that are normal after
menopause are flagged high. That accounts for the only 2 false positives (abnormal F1 0.989).

## R11 — OCR evaluation and fixes; FHIR export (2026-09-30)

**OCR evaluation** (`eval/ocr_eval.py`): the synthetic set had only 3 scanned reports, all bordered tables. Now 20
text-layer synthetic reports, spread over the five text layouts, are rendered to images and scanned at three seeded
levels, 60 scans in all:
* **clean:** 200 dpi, straight.
* **medium:** the generator's own scan effect: 150 dpi, 0.6–1.6° skew, noise, blur, JPEG 72.
* **heavy:** 150 dpi, 1.8–2.6° skew, stronger noise and blur, JPEG 55.

Each scan runs without the LLM and is scored against gold. The same reports' text layer is the paired control
(abnormal F1 1.00).

| Scan level | Abnormal F1 | Precision | Found (of 92) | False positives | Values exact | OCR s/page |
|---|---|---|---|---|---|---|
| clean, before → after | 0.60 → **0.92** | 0.56 → 0.95 | 60 → 82 | 48 → **4** | 71% → 89% | 12 |
| medium, before → after | 0.84 → **0.93** | 0.93 → 0.99 | 70 → 81 | 5 → **1** | 83% → 91% | 12 |
| heavy, before → after | 0.85 → **0.91** | 0.97 → 1.00 | 70 → 76 | 2 → **0** | 75% → 81% | 11 |

**What the first run found** (raw OCR output inspected):
1. **Text outside tables was dropped.** A page often comes back as one small table (the header) plus plain text
   lines, and `ocr_pdf` kept only the table rows. The plain layout scored 0%.
2. **Full-width digits came back spaced out, with a middle dot:** `１５８．０` → `1 5 8 · 0`. The parser kept `1`,
   which caused 42 of the 48 clean-scan false positives.
3. **Report words sometimes came back in simplified characters** (参考值, 红血球), so header columns went unrecognised.

All three are fixed in `ocr.py` post-processing (`clean_ocr_text`, `_text_outside_tables`). Text-layer PDFs are
unaffected. `tests/test_ocr.py` covers each case.

**After the fixes, value accuracy by layout:**

| Layout | clean | medium | heavy |
|---|---|---|---|
| standard | 100% | 100% | 78% |
| two-column | 72% | 77% | 73% |
| inline flags | 76% | 100% | 97% |
| full-width digits | 99% | 82% | 81% |
| plain | 100% | 97% | 97% |

**Remaining weakness:** rows dropped in two-column pages and in heavily degraded scans. These are missed values, not
invented ones: precision stays ≥ 0.95. The 5 remaining false positives come from values OCR misread, such as
84 → 8.4 or 152.1 → 1.

**FHIR export:** `fhir_export.py` writes findings as a FHIR R4 Bundle with one LOINC-coded Observation per value.
- `data/loinc_map.json` maps 122 of the 143 items (99 high, 23 medium confidence); 21 are left null on purpose.
- Every code was checked ACTIVE in LOINC 2.82. The bundles validate against `fhir.resources`.
- The Patient carries only gender; no header identity leaks (tested).
